On current OpenWrt openwrt-25.12, a correct home WPA3-Personal + 802.11r setup is:

- Same ssid on every roaming AP for that network
- Same encryption on every AP: sae for pure WPA3, or sae-mixed if you still need WPA2 clients
- Same key on every AP
- Same mobility_domain on every AP
- ieee80211r '1' on every AP
- Unique nasid per FT AP/BSS
- Do not force ft_psk_generate_local '1' for sae/sae-mixed
- Apply this only to the AP wifi-iface sections, not to the backhaul STA interface

Recommended minimal example for pure WPA3:

config wifi-iface
	  option device 'radio0'
	  option mode 'ap'
	  option network 'lan'
	  option ssid 'VerciNet'
	  option encryption 'sae'
	  option key 'your-passphrase'
	  option ieee80211r '1'
	  option mobility_domain '4f57'
	  option nasid 'wr3000p-5g'
	  option ft_over_ds '0'

For mixed WPA2/WPA3:

config wifi-iface
	  option device 'radio0'
	  option mode 'ap'
	  option network 'lan'
	  option ssid 'VerciNet'
	  option encryption 'sae-mixed'
	  option key 'your-passphrase'
	  option ieee80211r '1'
	  option mobility_domain '4f57'
	  option nasid 'wr3000p-5g'
	  option ft_over_ds '0'

For your three-node setup, each AP BSS should have its own nasid, for example:

- wr3000p-24
- wr3000p-5
- wr3000e-24
- wr3000e-5
- wr3000-24
- wr3000-5

What to avoid:

- Don’t set ft_psk_generate_local '1' on sae or sae-mixed
- Don’t mix sae on one AP and sae-mixed on another for the same roaming SSID
- Don’t change mobility_domain between APs
- Don’t configure FT on the WDS STA uplink itself

Important nuance:

- On current OpenWrt, if ft_psk_generate_local stays unset/false for sae/sae-mixed, OpenWrt will derive
r0kh/r1kh automatically from mobility_domain plus the shared secret material. In a normal home network,
you usually do not need to set r0kh/r1kh manually.
- ft_over_ds '0' is the safer default in practice unless you specifically need Over-DS and have verified
it works cleanly on your clients.

Q: should ft_psk_generate_local be setted up on wpa2-psk?
- sae / sae-mixed: do not set ft_psk_generate_local '1'
- psk2: ft_psk_generate_local '1' is the intended default path

Why:

- In current OpenWrt, ft_psk_generate_local is set by default only when auth_type == 'psk'.
- psk2 maps to auth_type='psk', so FT-PSK defaults to local generation.
- sae maps to auth_type='sae', and sae-mixed maps to auth_type='psk-sae', so they default to
ft_psk_generate_local=0.

More importantly, for sae/sae-mixed, if you force ft_psk_generate_local '1', OpenWrt skips the whole r0kh/
r1kh FT setup block. That is the opposite of what current OpenWrt expects for FT-SAE. This is also the
rationale from the OpenWrt 11r fix work: ft_psk_generate_local does not work correctly with SAE; the r0kh/
r1kh path must be used.

So the practical rule is:

- encryption 'sae': leave ft_psk_generate_local unset, or set 0
- encryption 'sae-mixed': leave it unset, or set 0
- encryption 'psk2': leave it unset, or set 1
- encryption 'psk': not relevant for 11r; that is WPA1-only and should not be used for FT roaming

- ieee80211r '1'
- same ssid, key, mobility_domain
- unique nasid per AP/BSS
- ft_psk_generate_local left at default for sae/sae-mixed so OpenWrt can derive r0kh/r1kh

Q: then if ft_psk_generate_local is unset then it requires r0kh and r1kh, even on a home setup where there isn't a radius server? 

Yes, on current OpenWrt, but that does not mean you need a RADIUS server.

For WPA3-SAE or sae-mixed with 802.11r:

- leave ft_psk_generate_local unset, or set it to 0
- OpenWrt then uses the r0kh/r1kh FT path
- if you did not set r0kh/r1kh manually, OpenWrt auto-generates them from:
  - mobility_domain
  - your shared key (or auth_secret if present)

So in a normal home multi-AP setup, no RADIUS is required. You just need:

- same ssid
- same key
- same mobility_domain
- unique nasid on each AP/BSS
- ieee80211r '1'

Example:

option encryption 'sae'
option key 'your-passphrase'
option ieee80211r '1'
option mobility_domain '4f57'
option nasid 'wr3000p-5g'
# leave ft_psk_generate_local unset
# leave r0kh/r1kh unset unless you want to manage them manually

What happens internally on current OpenWrt:

- if ft_psk_generate_local is false and r0kh/r1kh are missing, OpenWrt derives them automatically
- if neither key nor auth_secret exists, setup fails with FT_KEY_CANT_BE_DERIVED

For WPA2-PSK:

- ft_psk_generate_local '1' is the intended default
- that is why psk2 behaves differently from sae
