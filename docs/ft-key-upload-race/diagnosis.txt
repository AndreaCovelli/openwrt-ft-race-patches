On each AP, keep a live log running:

logread -f | grep -E 'key addition failed|failed to set key|failed to remove key|auth_alg=ft|AP-STA-|
deauth|disassoc|mt76|phy[01]-ap0'

If you want kernel messages only:

dmesg -w

What “good” looks like

- nl80211: kernel reports: key addition failed disappears
- roam still ends with AP-STA-CONNECTED ... auth_alg=ft
- no immediate AP-STA-DISCONNECTED right after FT association
- client traffic continues during roam, with at most a very short hiccup

What would look like an mt76 problem

- the old key addition failed log is gone, but roaming is still broken
- kernel starts logging things like:
  - failed to set key ... to hardware (...)
  - failed to remove key ... from hardware (...)
  - mt76... / mt7915... / mt798... warnings or errors around the roam time
- the client associates with auth_alg=ft, but then:
  - traffic is dead

That pattern means mac80211 accepted the key correctly, but the later hardware upload path is failing.

Fast practical test

1. Start continuous ping from the client to 192.168.1.16.
2. Walk the client between APs several times.
3. Check whether:
  - ping stays mostly continuous
  - logs show auth_alg=ft
  - no key addition failed
  - no new hardware key errors appear

Interpretation

- If the error disappears and roaming works: your mac80211 patch is sufficient.
- If the error disappears but roaming still breaks: likely mt76 or firmware/offload follow-up.
- If the same key addition failed still appears: the patch did not actually land or did not match the
running source.
